# Постановка: ИИ-агент для соцсетей бренда (этап 1 — Telegram)

Составлено 3 октября 2026. Исполнитель читает `AGENTS.md` и этот документ целиком
перед началом. Коммитить и пушить нельзя. Новые зависимости запрещены (см. §12).

## 1. Цель

Агент ведёт Telegram-канал бренда Матемации для двух аудиторий: **ученики** и
**родители**. Главный критерий успеха — **минимум ручной работы человека**:

- человек тратит на канал не больше 15–25 минут в неделю в первый месяц и
  5–10 минут после включения автопубликации безопасных рубрик;
- всё утверждение делается кнопками в Telegram, без захода в админку;
- агент сам отсеивает черновики, которые не прошли проверку, и не показывает их.

Этап 1 строит **ядро, пригодное для других площадок**, но реализует только
Telegram. Видео-площадки (VK Клипы, Rutube, Дзен, YouTube, TikTok) в этап 1 не
входят; под них закладываются только модели и интерфейс адаптера (§9).

## 2. Жёсткое разделение с `ai_mentor`

Агент соцсетей — **отдельный агент**, не часть ИИ-наставника.

- Новое приложение `apps/social_agent`. Из `apps.ai_mentor` не импортировать
  ничего: ни провайдеры, ни `privacy`, ни настройки.
- Свои настройки с префиксом `SOCIAL_AGENT_*`, свой API-ключ LLM, свои промпты,
  своя статистика расходов.
- Провайдер LLM — **собственная реализация** по тому же принципу, что в
  `apps/ai_mentor/providers.py` (dotted path в настройке, Mock по умолчанию,
  stdlib `urllib`, форматы `openai` и `yandexgpt`). Копировать идею, не код через импорт.
- **Данные учеников и родителей агенту недоступны вообще.** Не читать модели
  `accounts`, `progress`, `practice` и другие пользовательские данные. Агент
  работает только с публичным материалом: опубликованными задачами и уроками,
  текстами, которые ввёл сотрудник, и настройками бренда. Это не
  переиспользование `scrub` из наставника, а исключение самой возможности утечки.

## 3. Пользовательский сценарий

1. Раз в неделю агент строит сетку публикаций на ближайшие 7 дней по рубрикам и
   создаёт черновики.
2. Каждый черновик проходит автоматическую проверку (§7). Не прошедшие проверку
   либо переписываются автоматически (не более 2 попыток), либо помечаются
   «нужен человек» с причиной.
3. Прошедшие проверку черновики приходят **в служебный Telegram-чат** с кнопками
   «Опубликовать», «Переписать», «Отклонить».
4. Человек нажимает кнопки. «Переписать» принимает короткий комментарий
   ответом на сообщение, например «короче и веселее».
5. Одобренный пост публикуется в канал в назначенное время.
6. После первого месяца человек может включить автопубликацию для отдельных
   безопасных рубрик (§6.3). Остальное по-прежнему идёт через кнопки.

## 4. Объём работ

В объёме:

- приложение `apps/social_agent`: модели, миграции, админка, сервисы, задачи Celery;
- провайдер LLM с мок-реализацией;
- источники контента и проверки (§7);
- Telegram-адаптер публикации и бот утверждения (§8);
- тесты (§11).

Вне объёма:

- любые видео-площадки и генерация видео;
- генерация изображений и рендер формул в картинки (нужна библиотека, отдельное решение);
- сбор просмотров канала (в Bot API нет такого метода; проверить по актуальной
  документации и только записать как ограничение, §9.3);
- сбор данных из интернета и новостей;
- ответы на комментарии и личные сообщения подписчиков;
- платная реклама, покупка размещений;
- изменение моделей и поведения других приложений.

## 5. Модели (`apps/social_agent/models.py`)

Не создавать дублирующих моделей. Переиспользовать `Assignment` и `Lesson` из
`apps.content` только через внешний ключ и только на чтение.

**`BrandProfile`** (одна запись, редактируется в админке).
Название бренда, описание, тон голоса (текст), примеры хороших постов (текст),
запретные темы и формулировки (список), имена конкурентов (список, чтобы не
упоминать), подпись, список хэштегов, дата ЕГЭ для отсчёта (`exam_date`, пусто
по умолчанию — отсчёт тогда отключён), язык (`ru`).

**`Channel`**: `platform` (choices: `telegram`, `vk_clips`, `rutube`, `dzen`,
`youtube`, `tiktok`; реализован только `telegram`), `title`, `external_id`
(для Telegram — `@username` или числовой id), `is_active`, `mode`
(`manual` / `auto_safe`, по умолчанию `manual`). Активировать канал площадки
без реализованного адаптера нельзя (валидация в `clean()`).

**`Rubric`**: `slug`, `title`, `audience` (`students` / `parents` / `both`),
`source_kind` (см. §6.1), `prompt_hint`, `risk` (`low` / `high`),
`autopublish_allowed` (bool; допустимо `True` только при `risk=low`, это
проверяется в `clean()`), `is_active`.

**`RubricSlot`**: `rubric`, `channel`, `weekday` (0–6), `time` (местное время),
`is_active`. Планировщик создаёт посты по слотам.

**`SocialTaskPermission`**: `assignment` (FK на `content.Assignment`, один к
одному), `approved_by`, `approved_at`. **Только задача с такой записью может
попасть в пост.** Это защита от публикации чужих или лицензионных условий:
разрешение на публичное использование даёт человек явно.

**`ContentIdea`**: `title`, `body`, `audience`, `rubric` (необязательно),
`used_at`. Идеи вводит сотрудник в админке; агент берёт их как источник.

**`Post`**: `channel`, `rubric`, `kind` (`text` / `image` / `video`; в этапе 1
создаётся только `text`), `status`, `text`, `scheduled_for`, `published_at`,
`external_message_id`, `source_ref` (строка вида `assignment:123`),
`group_key` (UUID для будущей кросс-публикации одного материала), `rewrite_count`,
`review_notes`, `failure_reason`, `created_at`, `updated_at`.

Статусы и допустимые переходы (реализовать как явную таблицу переходов в
сервисе, любые другие запрещены):

```
draft -> checking -> needs_review -> approved -> scheduled -> published
                  \-> needs_human   (не прошёл проверку, нужен человек)
needs_review -> rejected | rewriting -> checking
scheduled -> failed -> scheduled   (повтор)
```

**`PostCheck`**: `post`, `kind` (`banned_phrase`, `number_whitelist`,
`answer_integrity`, `length`, `competitor`, `personal_data`), `passed`, `detail`.

**`LlmCall`**: `purpose` (`draft`, `rewrite`, `check`), `model`, `prompt_tokens`,
`completion_tokens`, `cost` (по `SOCIAL_AGENT_COST_PER_1K_*`, как в наставнике, но
свои настройки), `post` (необязательно), `created_at`. Тексты промптов целиком не
хранить, только метаданные.

**`MediaAsset`** (заготовка под видео): `post`, `kind` (`image` / `video`),
`file` (`FileField`), `duration_seconds`, `width`, `height`. В этапе 1 только модель
и админка, без логики.

**`BotState`**: `key`, `value`. Хранит `last_update_id` бота.

## 6. Планирование и источники контента

### 6.1. Источники (`sources.py`)

Общий интерфейс `ContentSource.fetch(rubric, on_date) -> SourceMaterial | None`.
`SourceMaterial` хранит `facts` (словарь допустимых фактов и чисел) и
`reference_text`. Реализовать:

- `assignment_of_day` — берёт задачу **только** из `SocialTaskPermission`, часть 1,
  с `correct_answer` и `reference_solution`; не берёт ту, что уже публиковалась
  за последние 60 дней. Ответ и разбор в `facts` берутся из базы, а не от LLM.
- `lesson_tip` — короткое методическое правило из опубликованного
  `TheoryBlock` / `Lesson` (`status=PUBLISHED`), только если урок имеет флаг
  разрешённых к публикации материалов: для этого завести аналог
  `SocialTaskPermission` для уроков (`SocialLessonPermission`).
- `exam_countdown` — число дней до `BrandProfile.exam_date`; если дата не задана,
  источник возвращает `None`, пост не создаётся.
- `staff_idea` — следующая неиспользованная `ContentIdea`.
- `evergreen` — вечнозелёные темы из `BrandProfile` для родителей: режим,
  мотивация, как помогать ребёнку. Без обещаний результата.

Пока в базе нет разрешённых задач, рубрики с источником `assignment_of_day`
просто пропускаются, а не заполняются выдумкой.

### 6.2. Планировщик (`planner.py`, задача Celery)

- `plan_week()` создаёт черновики на ближайшие 7 дней по активным `RubricSlot`.
- **Идемпотентна:** повторный запуск не создаёт дубликатов (ключ — канал, рубрика,
  дата и время).
- Запускается из `CELERY_BEAT_SCHEDULE` раз в неделю, по воскресеньям вечером.
- Не создаёт посты на прошедшее время и не падает, если источник вернул `None`.

### 6.3. Автопубликация

Автоматически без человека публикуется пост только если выполнены **все** условия:

1. `SOCIAL_AGENT_PUBLISH_ENABLED=1`;
2. `Channel.mode == "auto_safe"`;
3. `Rubric.risk == "low"` и `Rubric.autopublish_allowed`;
4. все `PostCheck` пройдены;
5. в тексте нет ни одного числа, которого нет в `facts` источника (§7.3).

По умолчанию все каналы в режиме `manual`. Режим переключает человек в админке
после месяца ручной работы. Агент сам режим не меняет.

## 7. Проверки (`checks.py`)

Чистые функции без обращения к сети. Каждая пишет `PostCheck`.

1. **Запретные формулировки.** Гарантии баллов («гарантируем», «100 баллов»,
   «сдашь на ...»), цены и скидки, медицинские и психологические обещания, всё из
   `BrandProfile.forbidden_*`.
2. **Конкуренты.** Совпадения с `BrandProfile.competitors` (нормализация регистра).
3. **Белый список чисел.** Каждое число в тексте поста (кроме даты публикации и
   номеров списка) должно присутствовать в `facts` источника. Иначе
   `needs_human`. Так LLM не может выдумать статистику, цифры результатов или
   неверную арифметику.
4. **Целостность ответа задачи.** Пост рубрики `assignment_of_day`: если ответ
   раскрывается, он должен совпасть с `correct_answer` (через
   `Assignment.check_answer`); в «вопросительной» версии ответа в тексте быть
   не должно.
5. **Длина.** До 4096 символов (лимит Telegram), рекомендованная — по рубрике.
6. **Личные данные.** Адреса почты, телефоны, ссылки с токенами в тексте поста.

LLM-проверка («похож ли текст на голос бренда») допускается как мягкий сигнал, но
не как единственная защита.

**Формулы.** В Telegram нет LaTeX. Прежде чем писать код рендера, изучить скилл
`math-input-and-rendering` и разметку в `apps/knowledge/markup`. Если условие
задачи нельзя безопасно перевести в Unicode-текст, пост получает статус
`needs_human` с причиной `formula_render`, а не публикуется кривым. Рендер
в картинки — отдельный этап.

## 8. Telegram

### 8.1. Адаптер публикации (`adapters/telegram.py`)

- Интерфейс `ChannelAdapter` с методами `publish(post) -> PublishResult` и
  свойством `capabilities` (`text`, `image`, `video`). Реестр адаптеров по
  `Channel.platform`.
- Реализация на `urllib` через Bot API (`sendMessage`, `parse_mode=HTML`,
  экранирование пользовательского текста).
- При ответе 429 учитывать `retry_after`; при сетевых ошибках повторить с
  ограниченным числом попыток; ошибки сохранять в `failure_reason`.
- **Публикация ровно один раз:** переход `scheduled -> published` под
  `select_for_update`, `external_message_id` записывается в той же транзакции,
  повторная задача на опубликованный пост ничего не делает.

### 8.2. Бот утверждения (`bot.py`)

- Токен — `SOCIAL_AGENT_TELEGRAM_BOT_TOKEN` из окружения. **Никогда не писать токен
  в логи, ответы и тесты.**
- `SOCIAL_AGENT_REVIEW_CHAT_IDS` и `SOCIAL_AGENT_REVIEWER_USER_IDS` — списки
  разрешённых чатов и пользователей. Нажатие кнопки от любого другого
  пользователя игнорируется и логируется.
- Сервер на TimeWeb пока не создан, публичного адреса для webhook нет. Поэтому
  использовать **long polling**: функция `process_updates()` + management-команда
  `run_social_bot`, работающая в цикле. Смещение хранится в `BotState`.
- Callback-кнопки: «Опубликовать» (`approve`), «Переписать» (`rewrite`, затем
  комментарий ответом), «Отклонить» (`reject`). Данные кнопки содержат только id
  поста и действие.
- В служебный чат отправляется только то, что нужно для решения: текст поста,
  рубрика, время, результат проверок. Токены и ключи не показывать.

## 9. Видео и другие площадки (только фундамент)

- Модели `Channel.platform`, `Post.kind`, `MediaAsset`, `Post.group_key` и реестр
  адаптеров должны позволять добавить площадку **одним новым адаптером без
  изменения ядра**. Проверить это тестом на фиктивном адаптере.
- Адаптеры VK Клипы, Rutube, Дзен, YouTube, TikTok в этапе 1 не создавать.
- Известные ограничения для будущих этапов (проверять по актуальным
  документам, не принимать на веру):
  - TikTok: публичная публикация через API требует аудита приложения, до него
    публикации приватные;
  - YouTube: проект без верификации загружает видео как приватные;
  - Instagram и Facebook в РФ признаны экстремистскими, площадку не
    реализуем.
- Метрики. В Bot API, по моим данным, нет метода для просмотров поста в канале;
  Codex должен проверить это в актуальной документации и записать вывод в
  комментарий модуля. Если просмотры недоступны, в этапе 1 только ручные поля
  `Post.views` и `Post.reactions` в админке.

- Задачи агента идут в отдельную очередь `social`, чтобы их сбой не влиял на

- Добавить пример переменных в существующий файл примера окружения (если он есть),

## 11. Тесты

Обязательны, все без сети (подменяемый transport, `MockProvider`):

- переходы статусов: допустимые проходят, недопустимые бросают исключение;
- планировщик идемпотентен; пропускает источник `None`;
- каждая проверка из §7 на положительных и отрицательных примерах;
- белый список чисел: выдуманное число даёт `needs_human`;
- публикация ровно один раз при повторном запуске задачи и при конкуренции;
- 429 с `retry_after` и сетевые ошибки в адаптере Telegram;
- бот: чужой пользователь не может нажать кнопку; корректные кнопки меняют статус;
- `SOCIAL_AGENT_PUBLISH_ENABLED=0` не отправляет ничего в канал;
- автопубликация срабатывает только при выполнении всех условий §6.3;
- `autopublish_allowed` нельзя поставить для `risk=high`;
- задача без `SocialTaskPermission` никогда не попадает в пост;
- агент не читает модели пользователей (тест на импорты приложения);
- фиктивный адаптер добавляется без изменения ядра;
- токен бота не появляется в логах.

Перед завершением обязательно запустить:

```powershell
.\scripts\test.ps1
```

## 12. Ограничения

- Новых зависимостей нет: `urllib`, Celery и `sympy` уже в проекте. Если
  понадобится что-то ещё (рендер формул, MTProto для просмотров), остановиться и
  сообщить, не ставить.
- Миграции только создающие новые таблицы; существующие не менять.
- Только PowerShell-совместимые команды и `pathlib`; без WSL.
- `.env` не читать и не печатать.
- Не коммитить, не пушить, не менять ветки.
- Бизнес-логика — в сервисах, не в админке, представлениях и шаблонах.

## 13. Критерии приёмки

1. На чистой базе с `MockProvider` одна команда создаёт план недели; черновики
   приходят в служебный чат (в тесте — в подменённый transport).
2. Нажатие «Опубликовать» ведёт к публикации в назначенное время, одному
   сообщению и одной записи с `external_message_id`.
3. «Переписать» с комментарием создаёт новую версию, не более
   `SOCIAL_AGENT_MAX_REWRITES` раз.
4. Выдуманное число, запрещённая формулировка или упоминание конкурента ведут к
   `needs_human`, пост не доходит до канала.
5. Без `SocialTaskPermission` рубрика «задача дня» не создаёт постов.
6. При `SOCIAL_AGENT_ENABLED=0` и при `SOCIAL_AGENT_PUBLISH_ENABLED=0` ничего не
   публикуется.
7. Из `apps/social_agent` нет импортов из `apps.ai_mentor` и пользовательских
   моделей.
8. Все тесты, включая весь прежний набор, проходят: `.\scripts\test.ps1`.
