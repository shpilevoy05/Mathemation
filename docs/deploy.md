# Выкладка и эксплуатация

Документ описывает, как поднять Матемацию в проде и что делать, когда что-то
пошло не так. Всё, что здесь есть, лежит в `infra/production/`.

Схема: контейнеры приложения (веб, воркер, расписание) и nginx — свои; база и
Redis — управляемые сервисы облака. Своего Postgres рядом намеренно нет: иначе
появляются две правды о том, где лежат данные, и два набора бэкапов.

```
интернет → nginx (TLS, статика, internal-локация) → gunicorn (web)
                                                  ↘ celery worker
                                                  ↘ celery beat
   управляемый Postgres          управляемый Redis (кеш + брокер)
```

---

## 1. Что должно быть до первой выкладки

| Что | Зачем |
|---|---|
| Управляемый PostgreSQL 16+ | боевая база; SQLite процесс не примет |
| Управляемый Redis | общий кеш (без него лимиты частоты не лимиты) и брокер Celery |
| Корневой сертификат провайдера базы | `sslmode=verify-full` без него не работает |
| TLS-сертификат домена | `infra/production/certs/fullchain.pem` и `privkey.pem` |
| Сервер с Docker и Docker Compose | сами контейнеры |
| Каталог для бэкапов вне этого сервера | копия, переживающая потерю сервера |

Окружение: скопировать `infra/production/env.example` в `.env.production` в
корне репозитория (compose читает его именно оттуда) и заполнить. Файл в
`.gitignore` — это единственное место, где живут секреты, и в git он не
попадает.

Секреты, без которых процесс не стартует с `DJANGO_DEBUG=0`:
`DJANGO_SECRET_KEY` (не дев-ключ, не короче 50 символов), `DJANGO_ALLOWED_HOSTS`
(конкретные домены, не `*`), `POSTGRES_*`. С боевым эквайрингом обязателен
`BILLING_WEBHOOK_SECRET`. Проверки живут в `config/security.py` и падают на
старте, а не в момент первой ошибки.

### Почта

В разработке при `DJANGO_DEBUG=1` по умолчанию используется консольный
backend. В проде backend по умолчанию SMTP; его параметры задаются только
окружением:

| Переменная | Назначение |
|---|---|
| `EMAIL_BACKEND` | dotted path почтового backend; для прода — SMTP |
| `EMAIL_HOST`, `EMAIL_PORT` | адрес и порт SMTP-сервера |
| `EMAIL_HOST_USER`, `EMAIL_HOST_PASSWORD` | учётные данные SMTP; пароль является секретом |
| `EMAIL_USE_TLS`, `EMAIL_USE_SSL` | режим шифрования; одновременно включать оба нельзя |
| `EMAIL_TIMEOUT` | тайм-аут соединения в секундах |
| `DEFAULT_FROM_EMAIL` | отправитель пользовательских писем |
| `SERVER_EMAIL` | отправитель системных ошибок |
| `DJANGO_ADMINS` | получатели ошибок в формате `Имя <email>, ...` |

После настройки нужно запросить восстановление пароля для тестового аккаунта
и проверить доставку, отправителя и ссылку с боевым HTTPS-доменом. Лимит
запросов управляется `PASSWORD_RESET_MAX_ATTEMPTS` и
`PASSWORD_RESET_BLOCK_SECONDS`; страница всегда отвечает одинаково и не
сообщает, зарегистрирован ли адрес.

При `DJANGO_DEBUG=0` и непустом `DJANGO_ADMINS` ошибки уровня `ERROR` из
`django.request` отправляются администраторам через тот же SMTP. Структурные
логи в stdout при этом продолжают писаться.

### Первый запуск пустой базы

После готовности окружения действия выполняются строго по порядку:

```sh
python manage.py migrate
python manage.py bootstrap_reference
python manage.py createsuperuser
```

`bootstrap_reference` загружает разметку графа, профиль экзамена, траектории,
витрину магазина и платёжные справочники. Команда идемпотентна и не создаёт
демо-пользователей, попытки, проверки эксперта или домашки. До применения
можно посмотреть результат через `python manage.py bootstrap_reference --dry-run`.
После входа суперпользователь или методист создаёт приглашения ученикам и
родителям в панели. `seed_demo` на реальном сервере запускать нельзя.

## 2. Выкладка

```sh
cd /srv/matemacia
git fetch --tags && git checkout <тег>
export APP_VERSION=<тег>

# 1. Сборка образа (статика собирается внутри образа)
docker compose -f infra/production/docker-compose.yml build

# 2. Миграции и проверка прод-настроек — один процесс, до старта реплик
docker compose -f infra/production/docker-compose.yml run --rm release

# 3. Перезапуск сервисов
docker compose -f infra/production/docker-compose.yml up -d

# 4. Проверка
curl -fsS https://matemacia.ru/healthz   # процесс жив
curl -fsS https://matemacia.ru/readyz    # база и кеш отвечают
```

Порядок важен. `release` выполняет миграции ровно один раз: параллельный
`migrate` из трёх реплик — это гонка на схеме. `check --deploy` там же
проверяет security-настройки на реальном окружении, а не на дев-значениях.

`beat` запускается в одном экземпляре. Две копии означают две ночные
пересборки плана и двойные начисления.

Очередь `social` обслуживает отдельный `social-worker` с одной репликой, а
основной `worker` слушает только `celery`. Поэтому сбой Telegram или LLM не
занимает процессы, выполняющие задачи основной платформы.
Long polling согласования выполняет отдельный процесс `social-bot`.

Из частых задач в расписании только уборка арены (`sweep_arena`, каждые пять
минут): она снимает партии, которые никто не открыл, и брошенные заявки на
случайного соперника. Ежедневная `rotate_leagues` (00:10) закрывает сезон лиги
и подводит итоги месяца — без неё сезон не закроется сам, награды не выдадутся,
а таблица так и будет показывать прошлый месяц. Задача идемпотентна и ничего не считает — если `beat`
не запущен, арена продолжает работать, но в списке партий копятся ожидания,
к которым никто не подошёл.

### ИИ-наставник и бюджет

По умолчанию используется `apps.ai_mentor.providers.MockHintProvider`. Для
боевого провайдера задайте
`AI_MENTOR_PROVIDER=apps.ai_mentor.providers.LLMHintProvider`, дневной лимит
`AI_MENTOR_DAILY_HINT_LIMIT` и тарифы в рублях
`AI_MENTOR_COST_PER_1K_INPUT` / `AI_MENTOR_COST_PER_1K_OUTPUT`.

YandexGPT:

```text
AI_MENTOR_LLM_FORMAT=yandexgpt
AI_MENTOR_LLM_BASE_URL=https://llm.api.cloud.yandex.net/foundationModels/v1/completion
AI_MENTOR_LLM_API_KEY=<секрет>
AI_MENTOR_LLM_FOLDER_ID=<идентификатор каталога>
AI_MENTOR_LLM_MODEL=yandexgpt-lite
```

OpenAI-совместимый DeepSeek:

```text
AI_MENTOR_LLM_FORMAT=openai
AI_MENTOR_LLM_BASE_URL=https://api.deepseek.com/chat/completions
AI_MENTOR_LLM_API_KEY=<секрет>
AI_MENTOR_LLM_MODEL=deepseek-flash
```

Тайм-аут, максимум токенов и температура задаются переменными
`AI_MENTOR_LLM_TIMEOUT_SECONDS`, `AI_MENTOR_LLM_MAX_TOKENS` и
`AI_MENTOR_LLM_TEMPERATURE`. Расход за сегодня и семь дней виден методисту в
панели в блоке «Наставник: расход».

### Персональные данные и ИИ

Во внешний LLM уходят только очищенные условие задачи, эталонный разбор,
вопрос ученика и последние сообщения текущей сессии. Имя, фамилия, логин,
почта, телефон, данные родителей и внутренние идентификаторы аккаунта не
передаются. Для OpenAI-совместимых API поле `user` содержит необратимый
псевдоним вида `stu_…`; YandexGPT не получает даже его.

Задайте отдельный секрет `AI_PRIVACY_PSEUDONYM_KEY`. Если он пуст, приложение
выводит отдельный ключ из `DJANGO_SECRET_KEY` через HMAC, не используя основной
секрет напрямую. Метаданные запроса без текста промпта сохраняются локально в
`AiOutboundRequest`: request UUID, псевдоним, провайдер, модель, число удалений
и токены. При расследовании сотрудник находит псевдоним в read-only разделе
Django Admin; программный поиск выполняет `student_for_pseudonym()`.

### Юридический шлюз

`LEGAL_CONSENT_ENFORCED` можно задать явно: по умолчанию он выключен при
`DJANGO_DEBUG=1` и включён при `DJANGO_DEBUG=0`. Изменение версии документа
по-прежнему повторно запрашивает согласие у учеников и родителей.

## 3. Откат

Схема и код версионируются по-разному, поэтому и откат разный.

**Код без миграций** — вернуть предыдущий тег и перезапустить:

```sh
export APP_VERSION=<предыдущий тег>
git checkout <предыдущий тег>
docker compose -f infra/production/docker-compose.yml up -d --build
```

**Код с миграциями.** Миграции пишутся совместимыми со старым кодом на один
релиз вперёд: сначала добавить поле и научиться жить без него, и только
следующим релизом удалять старое. Тогда откат кода не требует отката схемы.
Если совместимость всё-таки нарушена — откатывается схема:

```sh
docker compose -f infra/production/docker-compose.yml run --rm release \
    python manage.py migrate <приложение> <номер предыдущей миграции>
```

Откат миграции, удаляющей данные, невозможен по определению: в этом случае
восстанавливаемся из копии (раздел 4). Поэтому такие миграции требуют
отдельного подтверждения владельца и снятия копии перед выкладкой.

## 4. Бэкапы и восстановление

Снятие — `infra/production/backup.sh`, ежедневно по cron:

```
20 3 * * * /srv/matemacia/infra/production/backup.sh >> /var/log/matemacia-backup.log 2>&1
```

Копия содержит дамп базы (`pg_dump --format=custom`), архив работ учеников,
контрольные суммы и оглавление дампа. Оглавление снимается сразу после дампа:
непроверенная копия — это надежда, а не бэкап. Хранение — 30 дней
(`BACKUP_KEEP_DAYS`), каталог с копиями должен уезжать за пределы сервера.

Снапшоты управляемой базы у провайдера — не замена: они живут в том же
аккаунте и под теми же правами, и ошибочное удаление кластера уносит и их.

Восстановление — `infra/production/restore.sh`:

```sh
./infra/production/restore.sh /srv/backups/matemacia/20260809-032000
```

По умолчанию разворачивается в базу `<имя>_restore`, а не поверх боевой:
учебная тревога не должна заканчиваться потерей продакшена. Скрипт печатает
запросы, которыми проверяется результат (число учеников, последняя попытка,
последний успешный платёж).

**Репетиция — раз в квартал.** Бэкап, который ни разу не разворачивали, не
считается рабочим. Учение — это `restore.sh` на пустую базу и три проверки из
его вывода; результат записывается с датой.

Целевые показатели: RPO 24 часа (суточные копии), RTO 2 часа (развернуть
копию и переключить окружение). Если нужен RPO меньше — включается
непрерывное архивирование WAL на стороне провайдера.

## 5. Что смотреть после выкладки

| Сигнал | Где | Что значит |
|---|---|---|
| `/readyz` вернул 503 | балансировщик | отвалилась база или Redis |
| `matemacia.security` в логах | stdout контейнера | блокировки перебора, подделка колбэка, действия бэкофиса |
| `matemacia.integrations` | stdout контейнера | выдача ссылок на видео, колбэки оплаты, вызовы наставника |
| `billing.webhook.bad_signature` | лог безопасности | кто-то пытается подтвердить оплату сам |
| рост 429 | лог nginx | лимиты частоты режут живых людей — пересмотреть `THROTTLE_*` |

Логи контейнеров ограничены (`max-size: 20m`, 5 файлов): без этого диск
кончается в самый неподходящий момент.

## 4a. Обновление предметной разметки

Разметка навыков лежит в коде (`apps/knowledge/markup/`), поэтому приезжает
вместе с образом. Применяется отдельным шагом в релизном контейнере — тем же,
где идут миграции:

```sh
docker compose -f infra/production/docker-compose.yml run --rm release   python manage.py load_markup --dry-run
docker compose -f infra/production/docker-compose.yml run --rm release   python manage.py load_markup
```

Сухой прогон обязателен: он показывает, что именно изменится в графе, по
которому у учеников уже накоплено освоение. Команда идемпотентна — повторный
запуск ничего не меняет и безопасен.

Узлы, исчезнувшие из новой версии книги, не удаляются сами: они попадают в
отчёт. Удалять их (`--prune`) стоит отдельным решением и только после того,
как понятно, куда девать историю учеников по ним.

## 4б. Банк вопросов по теории

Вопросы для квиза и «своей игры» тоже лежат разметкой в коде
(`apps/content/theory_bank.py`) и приезжают вместе с образом. Раскладываются
тем же релизным контейнером, что и разметка навыков:

```sh
docker compose -f infra/production/docker-compose.yml run --rm release \
  python manage.py load_theory_bank --dry-run
docker compose -f infra/production/docker-compose.yml run --rm release \
  python manage.py load_theory_bank
```

Команда идемпотентна: ключ — тема и текст вопроса, повторный запуск ничего не
дублирует и не трогает вопросы, заведённые методистом руками. Тема, которой нет
в справочнике, пропускается — это видно в отчёте команды. Без банка квиз и
«своя игра» честно откажутся начинаться, остальная арена работает.

## 4в. Смена структуры экзамена

Структура ЕГЭ (номера заданий, их баллы, шкала перевода) описана в
`apps/exams/blueprint.py` и приезжает вместе с образом. Раскладывается тем же
релизным контейнером:

```sh
docker compose -f infra/production/docker-compose.yml run --rm release \
  python manage.py load_exam_blueprint --dry-run
docker compose -f infra/production/docker-compose.yml run --rm release \
  python manage.py load_exam_blueprint
```

Сухой прогон показывает, сколько заданий останется без навыков графа: такое
задание даёт нулевой вклад в прогноз, и это повод обновить разметку навыков,
а не выкатывать молча.

Номера заданий в графе сначала переводит миграция
`knowledge.0007_renumber_ege_tasks_2027`, а исправление проекта демоверсии
ФИПИ 2027 применяет `knowledge.0010_repair_ege_tasks_2027`. Она явно различает
узлы, которые после `0007` стали неоднозначными: `deriv-graph` остаётся на 9,
`extrema` переносится с 9 на 17, `economics` — с 17 на 13. Та же миграция
перезагружает активный профиль и связи заданий с навыками. Обратная операция —
noop, потому что восстанавливать заведомо ошибочную разметку нельзя. Перед
выкладкой на боевой базе снимите бэкап (раздел 4).

Пока Рособрнадзор не опубликовал официальную таблицу перевода на 33 балла,
профиль помечен как неофициальный, и экран прогноза об этом пишет. Когда
таблица выйдет, правится `PRIMARY_TO_SCALED` в разметке и снимается флаг
`SCALE_IS_OFFICIAL`; профиль обновляется тем же `load_exam_blueprint`.

## 4г. Косметика и спрайт

Каталог аватаров, рамок и тем раскладывается по витрине командой:

```sh
docker compose -f infra/production/docker-compose.yml run --rm release \
  python manage.py load_cosmetics
```

Команда идемпотентна. Предметы, которых в каталоге больше нет, она снимает с
витрины, но не удаляет: они лежат в инвентарях учеников, и удалить их значило
бы отобрать купленное.

Сам спрайт `static/img/cosmetics.svg` лежит в репозитории собранным и едет в
образ как обычный статический файл — пересобирать его на боевом окружении не
нужно. Пересборка нужна только после правок в `design/svg/`:

```powershell
.venv\Scripts\python.exe manage.py build_cosmetics_sprite
```

Тест сравнивает собранный спрайт с исходниками и падает, если их забыли
пересобрать. Граница между дизайн-набором и платформой описана в
`docs/design-cosmetics.md`.

Миграция `economy.0004_remove_rocket_avatar` удаляет аватар «Ракета», которого
нет в новом наборе: тем, у кого он был надет, возвращается базовый аватар.
Откатить нельзя — картинки больше не существует.

## 5a. Второй фактор сотрудников

С `DJANGO_DEBUG=0` он включён по умолчанию (`TWO_FACTOR_ENFORCED`). Методист,
эксперт, `is_staff` и суперпользователь после ввода пароля попадают не в
бэкофис, а на настройку фактора: приложение-аутентификатор, ключ, код с
телефона. Правило проверяется middleware перед каждым запросом, поэтому
`/admin/` закрыт так же, как страницы панели. Ученик и родитель фактор не
проходят.

После подтверждения человек один раз видит восемь резервных кодов — они
заменяют телефон и в базе лежат только отпечатками.

Потерян телефон, резервные коды кончились:

```sh
docker compose -f infra/production/docker-compose.yml run --rm release   python manage.py reset_two_factor <логин>
```

Консоль сервера здесь и есть право на это действие; снятие пишется в журнал
действий с автором. Без этой команды единственный администратор, потерявший
телефон, не мог бы войти вообще — снять фактор в админке может только вошедший.

## 6. Регулярные работы

| Что | Как часто | Чем |
|---|---|---|
| Проверить, что бэкап снялся и суммы сходятся | ежедневно | лог `backup.sh` |
| Репетиция восстановления | ежеквартально | `restore.sh` |
| Обновление базового образа и зависимостей | ежемесячно | пересборка с `--pull` |
| Продление TLS-сертификата | по сроку | certbot на хосте, `docker compose restart nginx` |
| Ротация `DJANGO_SECRET_KEY` | при подозрении на утечку | смена разлогинивает всех: делается в окно |
| Сверка сотрудников со вторым фактором | ежеквартально | Django-админка, раздел «Two factor device» |

## 7. Локальная проверка манифеста

Прод-манифест — это Linux-контейнеры, но собрать и запустить их можно и с
Windows-машины, где есть Docker Desktop:

```powershell
docker compose -f infra/production/docker-compose.yml --env-file .env.production build
docker compose -f infra/production/docker-compose.yml --env-file .env.production run --rm release
```

Локальная разработка при этом не меняется: `gunicorn` лежит в отдельном
`requirements-production.txt` и на Windows не ставится, `scripts\test.ps1`
работает как раньше.
