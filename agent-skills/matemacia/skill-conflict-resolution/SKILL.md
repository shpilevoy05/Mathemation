# skill-conflict-resolution

## Назначение

Дать единственный воспроизводимый способ выбрать инструкцию, когда два скилла
требуют разного. Результат — явная запись о конфликте: кто победил, почему и
какие ограничения проигравшего скилла всё равно сохраняются.

## Когда активируется

- два и более активных скилла дают противоречащие указания;
- vendor-скилл предлагает решение, нарушающее продуктовый инвариант
  Математики;
- общий инженерный совет расходится с доменным скиллом;
- priority-кейс в `skill-routing-evaluation` не сошёлся;
- неясно, чью инструкцию применять первой при равной релевантности.

## Когда не активируется

- скиллы дополняют друг друга и противоречия нет;
- нужно только измерить, какие скиллы выбираются — это
  `skill-routing-evaluation`;
- конфликт в git-мердже файлов, а не в инструкциях;
- дубликаты скиллов без противоречия по сути — это
  `skill-deprecation-and-cleanup`;
- расхождение поведения Claude Code и Codex без противоречия инструкций — это
  `skill-cross-agent-consistency`.

## Входные данные

- список активных скиллов и их релевантных требований;
- текст противоречащих указаний (дословно);
- уровень каждого скилла в иерархии (продуктовый, доменный, архитектурный,
  vendor, общий);
- затрагиваемые продуктовые, security- и алгоритмические инварианты.

## Базовая иерархия

```text
1. Продуктовые и юридические инварианты Математики
2. Собственный доменный skill
3. Собственный архитектурный skill
4. Vendor skill конкретной технологии
5. Общая инженерная рекомендация
```

При равном уровне выигрывает более узкий по области применения скилл; при
равной узости — тот, чьи ограничения строже (безопасный по умолчанию выбор).
Security-ограничения не проигрывают никогда: они складываются, а не заменяются.

## Процедура

1. Выписать оба требования дословно, без пересказа.
2. Определить уровень каждого скилла по иерархии.
3. Проверить, действительно ли требования несовместимы, или их можно выполнить
   одновременно (частый случай: разные этапы одной задачи).
4. Выбрать победителя по иерархии.
5. Выписать ограничения проигравшего скилла, которые продолжают действовать.
6. Сформировать запись о конфликте и включить её в ответ пользователю.
7. Если конфликт системный (повторяется), передать в
   `skill-deprecation-and-cleanup` или уточнить описания скиллов.

Примеры разборов — в [references/examples.md](references/examples.md),
кейсы иерархии — в [tests/conflicts](../../tests/conflicts).

## Ожидаемый результат

```yaml
conflict:
  skills:
    - skill-a
    - skill-b
resolved_by: skill-a
reason: "Более высокий уровень доменного приоритета"
constraints_preserved:
  - ...
```

Запись обязательна в ответе пользователю: конфликт, разрешённый молча,
воспроизводится в следующей задаче.

## Запрещено

- молча смешивать противоречащие инструкции в компромисс;
- позволять vendor-скиллу переопределять продуктовый инвариант;
- разрешать конфликт по порядку загрузки файлов или по тому, какой скилл
  «сработал первым»;
- терять ограничения проигравшего скилла, если они не были причиной конфликта;
- ослаблять security-ограничение ради удобства реализации;
- откладывать решение в виде «сделаю оба варианта».

## Связанные скиллы

- `skill-routing-evaluation` — поставляет priority-кейсы и фиксирует
  число конфликтов;
- `skill-supply-chain-audit` — источник конфликтов с vendor-инструкциями;
- `skill-metadata-governance` — поле `conflicts_with` фиксирует известные пары;
- `skill-acceptance-suite` — включает conflict tests в приёмку;
- `skill-deprecation-and-cleanup` — устраняет систематические конфликты.

## Приоритет при конфликтах

Этот скилл описывает саму иерархию, поэтому стоит выше остальных governance-
скиллов и ниже продуктовых инвариантов. Конфликт этого скилла с vendor-скиллом
о «правильном способе разрешать конфликты» решается в пользу этого скилла.

## Критерии приёмки

- в ответе есть запись о конфликте в обязательном формате;
- уровень каждого участника конфликта назван явно;
- `constraints_preserved` не пуст, если у проигравшего скилла были ограничения
  вне предмета конфликта;
- ни один продуктовый или security-инвариант не ослаблен;
- для повторяющегося конфликта создана задача на правку описаний или
  объединение скиллов;
- кейс добавлен в `tests/conflicts`, если конфликт новый.
