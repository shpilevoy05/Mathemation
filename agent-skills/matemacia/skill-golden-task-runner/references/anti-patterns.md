# Анти-паттерны прогона контрольных задач

## 1. Подсказка в формулировке

«Используя safe-database-migrations, добавь поле» измеряет исполнение, а не
выбор скилла. Формулировка задачи — как у обычного пользователя.

## 2. Грязное рабочее дерево

Чужие незакоммиченные правки попадают в `changes` и делают вывод о поведении
агента недостоверным.

## 3. Правка отчёта после прогона

«Он же почти выбрал нужный скилл» — уже интерпретация. Сырые данные не
редактируются; интерпретация живёт в `review_notes`.

## 4. pass при нарушенном инварианте

Рабочий код с нарушенным продуктовым инвариантом — это `fail` с severity
`critical`. Иначе golden tasks не защищают продукт.

## 5. Разные формулировки для разных агентов

Сравнение теряет смысл. Формулировка фиксируется в каталоге задач и не
адаптируется под агента.

## 6. Прогон без версии системы навыков

Отчёт без `skills_version` нельзя сопоставить с изменениями скиллов, и
регрессия остаётся необъяснимой.

## 7. Молчаливое вмешательство

Подсказка агенту в середине прогона без записи в `manual_interventions`
превращает измерение в демонстрацию.

## 8. Только «удобные» задачи

Прогон подмножества из быстрых задач систематически исключает те области, где
инварианты нарушаются чаще всего: наставник, экспертная проверка, прогноз.
