# Анти-паттерны оценки routing

## 1. Подгонка кейсов под поведение агента

Кейс описывает требуемое поведение системы. Если агент выбрал не тот скилл,
меняется описание скилла, а не ожидание в кейсе.

## 2. Только положительные кейсы

Набор без negative-кейсов не измеряет false positive rate. Скилл, который
активируется всегда, покажет recall 1.0 и будет считаться отличным.

## 3. Один агент вместо двух

Скилл, объявленный в `applies_to` для обоих агентов, проверяется на обоих.
Иначе расхождения находит пользователь, а не тест.

## 4. Метрика вместо причины

«Precision 0.71» без разбора не приводит к правке. Каждый провал получает
причину из фиксированного списка: широкое описание, нет negative-условий,
пересечение областей, конкуренция с vendor-скиллом.

## 5. Удаление кейса, который стабильно падает

Стабильно падающий кейс — самый ценный. Он либо помечается `known_issue` с
датой и владельцем, либо приводит к правке скилла.

## 6. Игнорирование порядка применения

Состав скиллов может быть верным, а порядок — нет: vendor-рекомендация,
прочитанная раньше продуктового инварианта, ломает решение. Priority-кейсы
проверяют порядок.

## 7. Прогон с пропущенными наблюдениями

Отсутствие наблюдения по кейсу — failure. Иначе метрика считается по удобному
подмножеству.
