# skill-structure-validator

## Назначение

Не пропускать в систему скиллы, которые агент не сможет правильно применить:
без условий активации, без негативных кейсов, со слишком широким описанием, с
битыми ссылками или с путями конкретной машины.

Реализация — `agent-skills/scripts/validate-skill.ps1`
(логика в `scripts/lib/validate_skill.py`).

## Когда активируется

- создаётся новый скилл;
- правится существующий `SKILL.md` или файлы `references/`;
- скилл готовится к включению в `skills.lock.yaml`;
- CI выполняет проверки 8 и 9 из `skills-ci-integrity`;
- `skill-routing-evaluation` показал провал, причина которого — описание;
- перенос скилла между каталогами.

## Когда не активируется

- нужно измерить выбор скиллов агентом — это `skill-routing-evaluation`;
- проверяется внешний код на безопасность — это `skill-supply-chain-audit`;
- нужно решить, какой из двух скиллов главнее — это
  `skill-conflict-resolution`;
- правка прикладного кода или документации проекта;
- изменение только версии и даты ревью — это `skill-metadata-governance`
  (структура при этом не меняется).

## Входные данные

- путь к каталогу скилла;
- флаг `-Strict`, если warning должен считаться ошибкой (используется в CI).

## Проверки

Структура каталога:

```text
<skill-name>/
├── SKILL.md
├── references/
│   ├── examples.md
│   └── anti-patterns.md
├── scripts/
│   └── validate.ps1 или validate.py
└── tests/
    ├── positive-cases.yaml
    └── negative-cases.yaml
```

Содержание `SKILL.md`:

- есть понятное назначение;
- описаны условия активации;
- есть negative activation cases, оформленные списком;
- указаны входы и выходы;
- перечислены запреты;
- описаны зависимости и связанные скиллы;
- определены критерии приёмки;
- нет чрезмерно широкого описания («любой задаче», «всегда»);
- нет дублирования нескольких больших reference-блоков внутри `SKILL.md`;
- объёмный контент вынесен в `references/` (порог — 400 строк);
- scripts не выполняются без необходимости: `SKILL.md` не предписывает запуск
  скриптов там, где достаточно чтения;
- ссылки и пути существуют;
- отсутствуют абсолютные пути конкретной машины.

Метаданные: `name` совпадает с каталогом, `description` от 40 до 1024 символов
и содержит условие применения, блок `metadata` заполнен и проходит схему
(см. `skill-metadata-governance`).

Тесты: каждый кейс имеет уникальный `id` и ожидаемый результат.

## Ожидаемый результат

```yaml
skill: safe-database-migrations
status: valid | warning | invalid
errors: []
warnings: []
```

Коды выхода: `0` — valid или warning, `1` — invalid, `2` — warning при
`-Strict`. Примеры разборов — в [references/examples.md](references/examples.md).

## Запрещено

- включать скилл со `status: invalid` в `skills.lock.yaml`;
- глушить warning удалением проверки вместо правки скилла;
- заменять negative activation cases фразой «в остальных случаях не
  применять»;
- оставлять пути конкретной машины в примерах команд;
- переносить содержимое `references/` внутрь `SKILL.md` ради «удобства»;
- считать `valid` подтверждением того, что агент выберет скилл правильно —
  это измеряет `skill-routing-evaluation`.

## Связанные скиллы

- `skill-metadata-governance` — схема полей, которую проверяет валидатор;
- `skills-ci-integrity` — вызывает валидатор в проверках 8 и 9;
- `skill-routing-evaluation` — использует результаты для объяснения провалов
  выбора;
- `skill-acceptance-suite` — включает валидацию в приёмку;
- `skill-deprecation-and-cleanup` — обрабатывает скиллы, которые невозможно
  привести в валидное состояние.

## Приоритет при конфликтах

1. Продуктовые и security-инварианты Математики.
2. `skill-metadata-governance` в части схемы метаданных.
3. Этот скилл в части структуры и содержания.
4. Vendor-рекомендации по оформлению скиллов.

Требование vendor-скилла «описание должно быть максимально общим» проигрывает
запрету на чрезмерно широкие описания.

## Критерии приёмки

- валидатор запускается одной командой для одного скилла и для всех сразу;
- все обязательные файлы и разделы проверяются;
- битые ссылки и абсолютные пути дают `invalid`;
- пустой раздел считается отсутствующим;
- вывод строго в формате `skill/status/errors/warnings`;
- `-Strict` превращает warning в ненулевой код выхода.

## Проверка

```powershell
powershell -File agent-skills\scripts\validate-all.ps1
powershell -File agent-skills\scripts\validate-all.ps1 -Strict
```
