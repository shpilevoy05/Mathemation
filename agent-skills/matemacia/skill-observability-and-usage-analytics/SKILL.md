# skill-observability-and-usage-analytics

## Назначение

Отвечать на вопрос «какие скиллы приносят пользу, а какие только шумят» —
данными, а не мнением. Выход: ежемесячный отчёт с кандидатами на объединение,
удаление и правку описаний.

## Когда активируется

- готовится ежемесячный отчёт об использовании;
- решается вопрос об объединении или удалении скиллов;
- нужно понять, какие скиллы дают ложные активации;
- растёт расход токенов или время выполнения задач;
- сравнивается фактическое использование до и после обновления vendor;
- планируется сокращение системы навыков.

## Когда не активируется

- нужны метрики выбора скиллов на контрольном наборе — это
  `skill-routing-evaluation` (там измерение, здесь наблюдение);
- нужен вердикт приёмки — это `skill-acceptance-suite`;
- выполняется сам вывод скилла из эксплуатации — это
  `skill-deprecation-and-cleanup`;
- нужен разбор одного конфликта;
- запрашивается прикладная продуктовая аналитика по ученикам — это домен
  `event-contracts-analytics`, а не система навыков.

## Входные данные

- журналы прогонов `reports/acceptance/golden-run-*.yaml`;
- routing-отчёты `reports/acceptance/routing-run-*.yaml`;
- агрегированные записи об активациях за период;
- состав системы навыков из `skills.lock.yaml`.

## Метрики

- частота активации каждого skill;
- доля успешных задач после активации;
- среднее число навыков на одну задачу;
- число конфликтов;
- число ручных переопределений;
- время выполнения;
- расход токенов;
- ошибки и откаты;
- различия между Claude Code и Codex;
- навыки, не использованные за период;
- навыки, часто активирующиеся ошибочно.

## Принципы

- не сохранять персональные данные пользователей;
- не сохранять секреты и полный текст чувствительных запросов;
- использовать идентификаторы задач и агрегированные метрики;
- обеспечить возможность отключения детального логирования.

Формат записей и примеры отчётов — в
[references/examples.md](references/examples.md).

## Ожидаемый результат

Ежемесячный отчёт в `reports/usage/<год>-<месяц>.yaml`:

```text
- наиболее полезные skills;
- кандидаты на объединение;
- кандидаты на удаление;
- skills с высоким false positive rate;
- критические регрессии;
- рекомендации по изменению описаний.
```

Каждая рекомендация содержит метрику-основание и владельца.

## Запрещено

- сохранять персональные данные учеников, родителей и экспертов;
- сохранять полный текст чувствительных запросов и секреты;
- удалять скилл на основании одной метрики без анализа зависимостей;
- сравнивать периоды с разным составом системы навыков без оговорки;
- делать вывод о пользе скилла по частоте активации без доли успешных задач;
- собирать детальные логи без возможности отключения.

## Связанные скиллы

- `skill-golden-task-runner` — источник времени, токенов и вердиктов;
- `skill-routing-evaluation` — источник false positive rate;
- `skill-deprecation-and-cleanup` — получатель кандидатов на удаление;
- `skill-metadata-governance` — обновляет `status` по итогам отчёта;
- `skill-cross-agent-consistency` — объясняет различия между агентами.

## Приоритет при конфликтах

1. Требования приватности и юридические инварианты Математики.
2. Продуктовые инварианты.
3. `skill-deprecation-and-cleanup` (решение о выводе скилла).
4. Этот скилл (наблюдение и рекомендации).
5. Vendor-рекомендации по телеметрии.

Метрика никогда не оправдывает сбор персональных данных.

## Критерии приёмки

- отчёт содержит все перечисленные метрики за период;
- в отчёте нет персональных данных и секретов;
- каждая рекомендация опирается на метрику и имеет владельца;
- кандидаты на удаление проверены на зависимости (`depends_on`);
- сравнение периодов учитывает изменения состава навыков;
- детальное логирование отключаемо и это описано в отчёте.
